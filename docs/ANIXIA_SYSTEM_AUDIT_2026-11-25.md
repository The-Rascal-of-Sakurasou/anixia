# ANIXIA システム全体監査・再設計方針

調査日: 2026-11-25
対象: GitHub main / Supabase production project `anixia`
目的: 個別機能の追加を一旦抑え、カタログ収集・照合・品質管理・公開・配信の仕組みを再設計する。

> この文書は2026-11-25時点の読み取り調査に基づく。数値は変動する。ここに記した改善案は設計方針であり、未実装のものを実装済みとして扱わない。

## 2. 現在の構成

### アプリケーション
- 静的HTML/CSS/JavaScriptをGitHub Pagesで配信。
- Supabase PostgreSQL、Auth、RLS、RPC、Edge Functions、Cronを利用。
- 作品・話数・人物・キャラクター・制作会社・団体・シリーズ・外部ID・別名などを別テーブルで管理。
- 作品テーブル `anime` は32以上の属性群を持ち、作品情報・同期状態・画像/あらすじの出典情報が同居している。

### データソース管理
`catalog_sources` の状態:
- 承認・有効: AniList、しょぼいカレンダー、Wikidata、Wikimedia Commons
- 無効・保留: Annict、日本語Wikipedia、TMDB

この状態を正とし、保留ソースの同期を有効化しない。AniListは合意済みの画像照合・表示用途に限定し、作品情報の一括取得には使わない。人気度・ランキング値は外部APIから取り込まない。

### 自動処理
- 複数のEdge Functionが稼働中。
- Wikidata作品同期、Wikidataメタデータ拡充、Wikidata/しょぼいカレンダーの話数同期、AniList/Commonsの画像同期、季節同期、公式サイト同期などが存在。
- Cronには数分間隔のジョブが複数存在し、一部の旧・一時ジョブは停止済み。
- `catalog_sync_runs` の直近ログでは成功扱いでも、1,407候補を日本語タイトル不足等で保留している処理がある。status=succeeded は「データ品質が十分」や「候補が公開された」ことを意味しない。

## 3. 重要な問題

### P0: 公開・品質のボトルネック
1. 作品10,032件に対してポスター未登録7,425件。公開作品でも6,029件が未登録。
2. 個別エピソード32,101件に対して公開2件。現在の全件手動審査方針では、公開キューが実質的に滞留する。
3. 非公開候補1,417件のうち1,366件が日本語タイトル不足。現在の自動収集・タイトル補完が候補の公開可能性を改善できていない。
4. あらすじは321件。無断転載を避ける方針は維持し、あらすじ数を増やすために著作権のある文章をコピーしない。

### P0: データフローの分離不足
- `anime` に正規作品情報、外部同期値、同期時刻、画像の権利情報、あらすじの出典情報が混在している。
- フィールド単位で「どのソースが、いつ、どの値を提供し、手動修正されたか」を一元追跡する仕組みをさらに明確化する必要がある。
- 取得候補、正規化済み候補、重複判定、品質審査、公開の各段階を分離し、同期処理が直接公開データを変更しない境界を強化する。

### P1: 自動処理の運用制御
- 複数の短周期Cronが同時に実行され得る。ソースごとのレート制限だけでなく、ANIXIA側の同時実行数、処理ロック、再試行、バックオフ、キュー長を統合管理する。
- 旧ジョブ・一時ジョブ・本番ジョブを台帳化し、目的・所有者・有効状態・停止条件を明示する。
- `catalog_sync_runs` の status と、実際の品質改善件数・保留件数・公開件数を分離して監視する。

### P1: セキュリティ・DB運用
2026-11-25のSupabase Advisorで確認:
- SECURITY DEFINER関数のうち、anon実行可能なもの5件、authenticated実行可能なもの9件が警告対象。公開読み取りRPCとして意図したものもあり得るため、単純に無効化せず、関数ごとに権限・内部認可・検索パス・返却列・件数上限を確認する。
- RLS有効・ポリシーなしのテーブルが10件。privateスキーマの内部テーブルと、publicスキーマの内部管理テーブルを分け、Data APIへの露出とGRANTを確認する。
- 複数の許可ポリシー、外部キーの未カバーインデックス、未使用インデックスの警告がある。実アクセスパターンとクエリ計画を見て整理し、未使用だけを理由に即削除しない。
- `pg_net` がpublicスキーマにあるという警告がある。Cron/HTTP呼び出しへの影響を調査してから移動可否を判断する。

### P1: スキーマとmigration履歴
- 本番DBには2026-11-17以降のmigration履歴が多数ある。
- リポジトリの `supabase/migrations` の一覧と本番migration履歴に差がある可能性がある。今回の一覧取得ではリポジトリ側に古い日付のファイルが見えたため、migrationファイル全件と本番履歴の照合が必要。
- 直接SQLで変更したものも含め、本番DBとGit管理migrationの再現性を確認する。差分を把握するまでは破壊的なDDLや大規模なテーブル再構成を行わない。

## 4. 再設計後の標準パイプライン

次の段階を明確に分ける。

1. **Source adapters**: 承認済みソースごとに取得処理を分離。利用条件、取得間隔、最大ページ、停止条件を宣言的に管理。
2. **Raw ingestion / staging**: 取得した原データを候補として保存。既存の公開作品を直接更新しない。
3. **Identity resolution**: 外部IDを最優先に照合。タイトル・年・形式は補助情報とし、曖昧な一致は自動統合しない。
4. **Normalization**: 形式、日付、タイトル、言語、役割名などをANIXIA共通形式へ正規化。
5. **Field provenance**: フィールド単位でsource、source_record_id、source_url、取得日時、確認状態、ライセンス/帰属情報、手動ロックを記録。
6. **Quality gates**: 必須項目、形式・年の妥当性、重複、作品範囲、画像一致、権利情報を検証。理由コードを必ず残す。
7. **Review queue**: 人手確認が必要な候補だけを管理画面へ送る。確認不要な低リスク項目と、要確認の作品同一性・権利問題を区別。
8. **Canonical catalog**: 審査済みの値だけを正規テーブルへ反映。手動値を優先し、ソース同期で上書きしない。
9. **Publication**: 作品公開とエピソード公開の基準を別々に定義。信頼できる出典と構造化データの検証を満たす低リスクの各話は、将来的に自動公開できる設計を検討し、例外のみ人手審査にする。
10. **Serving layer**: 公開用RPC/ビューは安定した読み取り専用インターフェースにし、内部同期テーブルを直接公開しない。
11. **Observability**: 取得・照合・更新・保留・公開・失敗・レート制限・処理時間を別々に記録し、日次品質スナップショットとアラートに反映。

## 5. 画像同期の再設計

- 画像候補の検索と画像採用を分離する。
- AniListは画像照合・表示の許可範囲内でのみ使用する。
- Commonsはファイル単位でライセンス、作者、帰属、作品との一致、寸法、URLの応答を検証する。
- 画像候補には一致スコアと判定理由を保存する。タイトル一致だけで自動採用しない。
- 画像がない作品は再試行可能な状態で保持し、失敗理由（候補なし、曖昧一致、ライセンス不明、URL不通、形式不正）を区別する。
- 画像の利用条件を確認できない場合はフォールバック表示とし、取得のために利用条件を迂回しない。
- 画像取得ジョブはキュー化し、同じ作品・同じ候補を何度も検索しない。

## 6. エピソード公開の再設計

- 作品単位の話数と個別エピソードを別々に保持する。
- 取得済み個別エピソードを、作品単位の話数だけで生成しない。
- ソースID、話数番号、タイトル、放送日等の整合性を検証する。
- 信頼できるソースから完全な構造化データを取得できた場合の自動公開条件を定義する。
- 複数ソースで矛盾する場合、話数番号が不正な場合、特別編・総集編等の分類が不明な場合は審査キューへ送る。
- 32,099件の非公開エピソードを一括公開しない。まず出典・重複・タイトル・番号・作品との紐付けを集計し、サンプル検証する。

## 7. 実装フェーズ

### Phase 0 — 安全な現状把握
- 本番DBスキーマ、全RLS、GRANT、RPC、Cron、Edge Function、Storage、migration履歴を棚卸し。
- DBバックアップと復旧手順を確認。
- Git管理migrationと本番migration履歴を照合。
- 現行同期の停止条件・重複実行・更新対象を確認。
- 読み取り専用の品質レポートを作成。

### Phase 1 — 運用制御
- 同期ジョブ台帳、排他ロック、キュー、バックオフ、冪等性を整備。
- ソースごとの権利承認状態を実行時に強制。
- 失敗・保留・処理量を分けた監視を導入。
- 手動修正・公開状態の保護をテスト。

### Phase 2 — データ品質パイプライン
- staging候補と品質判定を正規カタログから分離。
- 外部IDを中心とした同一性解決を強化。
- フィールド単位の出典・手動ロック・更新履歴を導入。
- 画像候補と画像採用を分離。
- 作品・エピソード別の公開基準を定義。

### Phase 3 — 既存データ修復
- 既存10,032作品を欠損項目別にキュー化。
- 画像未登録7,425件、読み仮名不足、基本情報不足を優先順に処理。
- 非公開1,417件の理由を分類し、1,366件の日本語タイトル不足を調査。
- 個別エピソード32,101件を出典・重複・公開適格性で分類。
- 自動修復後に差分・件数・サンプルを検証。

### Phase 4 — 拡張
- 10,000件を超えた後の新規追加を、品質を維持しながら継続。
- 検索・詳細ページ・マイライブラリ・評価・クイズ・コミュニティの順で安定化。
- UI・SEO・パフォーマンスはデータ基盤と並行して段階的に改善。

## 8. 変更禁止・保護ルール

- 監査前に本番データを一括削除・一括公開・一括統合しない。
- 手動修正済みの値を同期で上書きしない。
- sourceが未承認・無効のときは取得処理を実行しない。
- 外部APIの人気度を取り込まない。
- AniListを画像用途以外に拡張しない。
- 作品名・年だけで自動重複統合しない。
- 出典・権利・一致を確認できない画像を登録しない。
- 既存のAuth/RLS/RPC/URLを後方互換性の確認なしに変更しない。
- migration履歴の差分確認前に大規模DDLを実行しない。

## 9. 次の着手項目

最初に行うのは機能追加ではなく、Phase 0の完了である。特に以下を先行する。

1. 本番DBとGit migrationの完全な照合。
2. Cron全件のジョブ名・実行間隔・有効状態・呼び出し先の台帳化。
3. 全Edge Functionのソース承認チェック、認証、同時実行制御、更新対象の監査。
4. 画像・エピソード・非公開候補の理由別品質レポート。
5. バックアップと復旧可能性の確認。

Phase 0の結果をレビューしてから、後方互換性のある小さなmigrationとEdge Function改修に進む。
