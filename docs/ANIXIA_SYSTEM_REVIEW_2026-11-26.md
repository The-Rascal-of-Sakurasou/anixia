# ANIXIA 全システム再監査・改善計画

監査日: 2026-11-26  
対象: GitHub `The-Rascal-of-Sakurasou/anixia` の main、公開サイト、Supabase production project `anixia`  
監査方式: 公開サイト・GitHubソース・Supabaseの読み取り専用調査  
変更範囲: この監査では本番DB・公開画面・同期ジョブを変更していない。

## 1. 結論

ANIXIAは作品データ10,000件超、作品・人物・キャラクター・制作会社・エピソード・視聴管理・クイズ・コミュニティ等を扱う基盤まで拡張されている。一方、現時点の最大の課題は機能不足ではなく、次の4点である。

1. **Git管理のmigrationと本番DBの履歴が一致していない。** 現状のままDB変更を続けると、新規環境の再構築・復旧・変更追跡が困難になる。
2. **作品データの欠損が大きい。** とくにあらすじとポスター画像が不足しており、登録件数だけではデータベースとしての完成度を測れない。
3. **DB権限・RPC・同期ジョブの運用を整理する必要がある。** RLSは有効だが、不要なテーブル権限、SECURITY DEFINER警告、複数ポリシー、複数の定期ジョブが残っている。
4. **フロントエンドの共通化と配信方式を整理する必要がある。** CSSの重複、二重読み込み、旧キャッシュ名、ページ単位の依存関係が保守性と表示更新に影響する。

したがって、最初に全体を一括置換するのではなく、**現状保全 → migration整合 → 権限と同期の整理 → データ品質改善 → 配信・UI最適化 → 全画面テスト**の順で進める。

## 3. 最優先：migration履歴の不整合

確認結果:
- GitHub `supabase/migrations`: SQLファイル117件
- Supabase本番: 適用履歴109件
- Git側に本番履歴と一致しないバージョンが多数存在
- 本番側にGit側のファイル名と一致しないバージョンが多数存在
- Git側に `20261118043000` の同一バージョン名を持つSQLファイルが2件存在

これは最重要の運用リスクである。ファイル数の差だけではなく、初期スキーマ作成・後続DDL・本番直接変更・ファイルのリネームや再採番の履歴を照合する必要がある。

**禁止事項**
- migration履歴を一括でrepair・削除・再適用しない。
- 本番スキーマをGit側のSQLだけで上書きしない。
- 重複バージョンを片方削除して終わりにしない。
- 再現性が確認できるまで大規模DDLを実行しない。

**必要な作業**
1. 本番DBのスキーマ・関数・トリガー・ポリシー・拡張・Cronをスナップショット化。
2. Git側の全migrationを内容ベースで分類（適用済み相当、未適用、旧版、重複、直接変更由来）。
3. 本番の実スキーマとmigrationの最終状態を照合。
4. 新規DBを安全に構築できるベースラインを別途作り、再現テストする。
5. 本番の履歴修復は差分と復旧手順を確定してから行う。

## 4. セキュリティ・権限

### 確認できたこと
- publicスキーマのテーブルはRLS有効。
- privateスキーマに管理者・クイズ正解・品質スナップショット等の内部テーブルがある。
- 内部テーブルはRLS有効かつ、anon/authenticatedへのテーブル権限がないものを確認。
- 管理者用SECURITY DEFINER関数は `private.is_anixia_admin()` による管理者判定を関数内で実施している。
- 公開作品検索RPCは公開済み作品を対象にする設計で、公開読み取り用途のSECURITY DEFINER関数がある。
- 同期用Edge Functionは `verify_jwt=false` のものがあるが、確認した主要同期関数はcron tokenのハッシュ照合または管理者認証を行っている。
- 管理者ユーザー管理Edge FunctionはJWTを検証し、Authユーザー確認と管理者RPC判定を行う。

### 要改善
- Supabase Advisorは、anon実行可能なSECURITY DEFINER関数7件、authenticated実行可能なSECURITY DEFINER関数11件を警告。公開読み取りRPCは意図されたものが含まれる。管理者RPCは内部管理者チェックを確認したが、全関数について返却列・件数上限・検索パス・実行権限を個別レビューする。
- `public.anime` はanon/authenticatedにSELECT・INSERT・UPDATE・DELETE権限が付与されている。RLSにより一般ユーザーの行操作は制限されているが、公開データの読み取りはRPCを経由する構成であるため、クライアント依存を再確認したうえで不要な直接権限を最小化する。
- 複数の許可RLSポリシーが同一テーブル・操作に存在する。現時点で即時の権限突破を意味しないが、ポリシー統合と評価コスト削減を検討する。
- Authの漏洩パスワード保護が無効というAdvisor警告がある。Auth設定と利用条件を確認して有効化を検討する。
- `pg_net` がpublicスキーマにあるという警告がある。CronのHTTP呼び出しに影響するため、依存関係を調べずに移動しない。
- RLS有効・ポリシーなしの10テーブルには内部管理用が含まれる。テーブル権限がないことを確認し、内部テーブルとして意図どおりであることを台帳化する。

## 5. DBパフォーマンス

Supabase Performance Advisor:
- 外部キーの未カバーインデックス: 15件
- 未使用インデックス: 24件
- 同一操作に複数の許可ポリシー: 24件

対応方針:
1. 作品一覧・検索・詳細・タイトル別名・エピソード・人物関連・視聴リストの実クエリを基準にする。
2. 外部キーインデックスはJOIN・削除・更新の実行計画を確認して追加。
3. 未使用インデックスは、アクセス履歴が短いことや未稼働機能を考慮し、即削除しない。
4. RLSポリシーは役割と操作単位で整理し、同じ条件を重複評価しない構造にする。
5. 検索は既存のサーバー側RPCを基準にし、全作品をブラウザに読み込む設計へ戻さない。
6. 一覧取得は小さなページサイズとkeyset paginationを基本とし、深いoffsetを避ける。

## 6. データソース・同期処理

### 現在のソース台帳
- 有効・承認: Wikidata、しょぼいカレンダー、AniList（画像用途）、Wikimedia Commons（条件を満たす画像）
- 無効・保留: Annict、TMDB、日本語Wikipedia

AniListは作品メタデータの一括収集に拡張しない。Commons画像は個別ファイルのライセンス・作者・帰属情報を確認する。Wikidataは構造化データに限定し、Wikipedia本文等の文章をコピーしない。

### 定期処理
本番Cronで有効なジョブは8件:
- AniListポスター同期（5分間隔）
- Commonsポスター同期（5分間隔）
- カタログ品質スナップショット（日次）
- 今期作品同期（日次）
- しょぼいカレンダーのエピソード同期（10分間隔）
- しょぼいカレンダーのタイトル同期（日次）
- Wikidataカタログ同期（10分間隔）
- Wikidataエピソード同期（10分間隔）

19件のEdge Functionsが登録されている。定期実行されていない関数・旧ソース用関数も残るため、機能名だけでなく、承認状態・Cron・認証方式・最終実行・更新対象・停止条件を台帳化する。

### 改善方針
- ソース別の取得処理と共通の同期制御を分離する。
- 同期は冪等にし、同一作品・同一外部IDの二重登録を防ぐ。
- 排他ロック、実行時間上限、同時実行数、バックオフ、429待機を統一する。
- 取得成功と、品質改善・候補追加・公開を別の指標として記録する。
- 手動修正済みフィールドを同期で上書きしない。
- 画像候補の検索と画像採用を分離し、候補一致・権利・帰属を記録する。
- 非公開候補は理由コードを保持し、審査対象だけを管理画面に表示する。
- 失敗・候補なし・曖昧一致・権利不明・再試行待ちを区別する。

## 7. フロントエンド・配信

### 現状
- GitHub Pages上の静的HTML/CSS/JavaScript
- Supabase JS v2をブラウザから利用
- 公開クライアントにはpublishable keyを使用
- 作品検索はサーバー側RPCを利用
- リポジトリサイズは約120,602 KB
- `site-theme.css` は約316 KB、`anixia-unified-theme.css` 約34.7 KB、`anixia-screen-system.css` 約12.2 KB、`anixia-design-refresh.css` 約26.7 KB

### 発見した改善点
- ホームHTMLで `performance.js` が重複して読み込まれている。
- 複数の共通CSSが同時に読み込まれ、テーマ・画面システム・リフレッシュCSSの役割が重複している。
- `sw.js` のキャッシュ名が `animecia-static-v44` のまま残っている。
- Service Workerはナビゲーションでキャッシュ済みページを優先して返すため、更新直後に古いHTMLが表示される可能性がある。
- ページごとにCSS/JSの読み込み方法が異なるため、全ページの共通基盤を一本化する必要がある。

### 再設計方針
1. 共通デザイントークン、ヘッダー、フッター、ボタン、フォーム、カード、通知、空状態を一元管理。
2. 旧CSSを即時削除せず、ページごとの参照を棚卸しして段階的に統合。
3. `performance.js` の重複読み込みを解消。
4. Service Workerのキャッシュ名と更新戦略を改め、HTMLはnetwork-first、静的アセットはバージョン付きcache-firstまたはstale-while-revalidateに分離。
5. 作品画像は遅延読み込み、適切なサイズ、固定アスペクト比、失敗時フォールバックを使用。
6. 作品一覧はページネーションまたは段階読み込みとし、初回に大量データを取得しない。
7. 静的SEOページは全件を毎回再生成せず、差分生成・分割sitemap・生成対象の明示を行う。
8. エラー・空データ・通信遅延時も操作不能にならないようにする。

## 8. 作品データモデル

現行の `anime` テーブルは作品の基本情報に加え、同期時刻、外部ソース、画像の出典・権利情報、あらすじの出典情報などを持つ。短期的に全面分割するのではなく、まず各フィールドの出典・更新者・確認状態・手動ロックを追跡できるようにする。

中長期的には以下の論理層を明確に分離する。
- 正規カタログ（作品・人物・キャラクター・制作会社・団体・シリーズ）
- 外部ID・別名・表記揺れ
- 取得候補・ステージング
- フィールド単位の出典・ライセンス・履歴
- 品質判定・審査キュー
- 公開状態
- 公開読み取り用RPC／ビュー
- ユーザー固有データ

同一性解決は外部IDを第一候補とし、タイトル・年・形式だけで自動統合しない。
